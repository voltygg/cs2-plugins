## 1. Why and the decisions

Today VoltMod is a static library and every plugin DLL embeds a full copy, including its own set of engine hooks. The user plans about twenty plugins of their own and wants other people to build on the framework, the way .NET apps run on one installed runtime. That needs one VoltMod per server process that plugins attach to.

**The guiding rule: move into the host only what must exist once per process. Everything else stays in the SDK, unchanged, until a real problem shows up.** When in doubt, leave it in the SDK.

**Clean cut.** The user is the only consumer today, and the framework and all three plugins change together in one tree. So: no fallbacks, no shims, no aliases, no forwarding headers, no temporary scaffolding, and never two ways to do one thing. When something is replaced, the old form is deleted in the same commit pair. A mismatch between host and plugin is an error with a clear message, not something to tolerate.

Decisions already made with the user. Do not reopen them; if one proves unworkable, stop and say why.

- **D1. Thin host, static SDK.** `voltmod.dll/.so` (the host) is the only Metamod plugin. It owns the eight engine hooks (installed once, fanned out), the frame tick, the cross-plugin service registry and plugin loading (phase 2), then the work every plugin would otherwise repeat: log output, gamedata resolution and schema verification (phase 3). The C++23 API (`Runtime`, `Players`, `Commands`, `Menus`, `Policy`, `Database`, game-event listeners, entity wrappers) stays a static library compiled into each plugin. Plugin source keeps compiling almost unchanged.
- **D2. The boundary is pure-virtual interfaces and plain data.** No `std::` type, exception, template or ownership transfer crosses it. Strings cross as pointer plus length and are copied by the receiver during the call. Callbacks cross as function pointer plus context pointer. Reasons, from the build settings: Linux uses the old libstdc++ string ABI with a static libstdc++ per module, where an empty `std::string` from one module is not recognised as empty by another; Windows `/MT` gives each module its own CRT. `ServiceExchange.hpp` already sets this rule for plugin-to-plugin calls.
- **D3. Plugins do not import `voltmod.dll`.** The host loads the plugin and passes `IHost*` to one `extern "C"` entry point. No import library, no search-path problem.
- **D4. Reload is in scope.** The old `meta unload` hang was fixed in Metamod (per the user; confirm the version in phase 0).
- **D5. Plugin home directories do not move.** `addons/<name>/{bin/<platform>/,configs/}` stays. A plugin loses `addons/metamod/<name>.vdf` and gains a small `addons/<name>/plugin.json`, generated by `voltmod_add_plugin`.
- **D6. Interfaces are written by hand.** Six small headers (three in phase 2, three in phase 3) do not justify a generator. An append-only lock check can come with third-party authors (section 5).
- **D7. `Logger<T>`, `Options<T>` and a small service container are SDK code** (phase 6, the user's call). They never touch the boundary.

## 3. Target shape

```text
Metamod
  └── voltmod        addons/voltmod/bin/<platform>/voltmod.{dll,so}     the only .vdf
        ├── eight engine hooks, installed once, fanned out
        ├── frame tick, service registry, plugin loader
        ├── log output, gamedata resolution, schema verification, each done once
        ├── admin-system   addons/admin-system/bin/<platform>/admin-system.dll
        ├── anticheat      ...
        └── bhop           ...        each = plugin code + static VoltMod SDK
```

### Boundary rules

1. An interface is a struct of pure virtuals with a protected non-virtual destructor and `static constexpr const char* InterfaceName = "VoltMod.IHostEvents"`, the `ServiceExchange` convention.
2. Parameters and returns are integers, fixed-width enums, `bool`, raw pointers to engine objects, and pointer-plus-length strings. Boundary headers include only `<cstddef>` and `<cstdint>`.
3. A subscription is `Token Subscribe(Fn* call, void* context)`, removed by token. The SDK wraps the token in the existing `Subscription`.
4. Host interfaces change freely. Any change bumps the single `AbiVersion` in the same commit, and the host refuses a plugin built against another value. Host and plugins always ship from the same build, so there is no append-only rule and no serving of old interface versions.
5. Game thread only. The SDK trampoline that calls back into plugin code catches exceptions, logs and continues.
6. The host never loads or unloads a plugin inside a fan-out; it queues the request for the start of the next frame. `volt reload` arrives inside the `DispatchConCommand` fan-out, and this rule is what makes it safe. It also makes `Exchange.Get<T>()` at the point of use safe: a pointer fetched and used inside one callback cannot dangle.

### The phase 2 interfaces

| Interface | Carries |
| --- | --- |
| `IHost` | `AbiVersion()`, the plugin's name and home directory, the Metamod `ISmmAPI*` and the KHook pointer (both are already stable cross-module interfaces, and they let `Runtime::Start` resolve engine interfaces exactly as it does today), `GetInterface(name)`, `ClaimCommand(name)` |
| `IHostEvents` | one subscribe method per engine hook: frame, server startup, client connected, disconnected, fully connected, settings changed, console command (returns whether it was consumed), check transmit |
| `IHostServices` | `Publish(name, pointer)`, `Unpublish(name)`, `Find(name)`, and a subscription raised whenever a service is published or withdrawn |

Each plugin's context in the host holds that plugin's tokens and published names. Unload runs the plugin's own teardown (unchanged order), then the host drops whatever the context still holds and logs each leftover as a leak, then frees the library.

Fan-out order is load order. A console command consumed by one plugin is not offered to the next, and the engine call is blocked once.

Three small pieces earn their place once there are many plugins:

- **Command names are claimed.** The SDK `CommandManager` calls `ClaimCommand` for each name it registers. If another plugin already holds it, registration fails with a log line naming both plugins, instead of two plugins silently answering `!ban`. Claims are released with the plugin's context.
- **Services changed.** `runtime.Exchange` gains a `Changed` event fed by the `IHostServices` subscription. Point-of-use `Get<T>()` stays the normal way; the event is for a plugin that wants to react when a peer appears or leaves (register with it, refresh a menu).
- **One status command.** `volt status [name]` prints each plugin's existing `StatusService` JSON through the descriptor's `Status` function.

### plugin.json

```json
{
  "name": "anticheat",
  "version": "1.1.0",
  "dependencies": [],
  "optionalDependencies": ["admin-system"]
}
```

Generated from `voltmod_add_plugin(anticheat VERSION 1.1.0 OPTIONAL_DEPENDS admin-system)` (`DEPENDS` for required ones) and read with glaze. The DLL path follows from `name`. The ABI version is not in the file; the binary's descriptor is the truth for that.

The host loads a plugin after the dependencies it lists that are installed; ties are alphabetical. A missing required dependency or a cycle refuses the affected plugins with one log line that names them. Unload is the reverse order. `volt unload` refuses while a loaded plugin requires the target, naming it; `volt reload` of such a plugin reloads its required dependents with it. The ordering is a plain topological sort, written SDK-free and unit-tested.

### Plugin entry

```cpp
struct VoltModPluginDescriptor
{
    uint32_t AbiVersion;   // the host refuses any value but its own, with a readable message
    bool (*Load)(IHost* host, char* error, size_t errorSize);
    void (*Unload)();
    const char* (*Status)();   // JSON text owned by the plugin, valid until the next call
};

extern "C" VOLTMOD_EXPORT const VoltModPluginDescriptor* VoltMod_PluginEntry();
```

`VOLTMOD_PLUGIN(PluginClass)` keeps its name and emits this instead of `PLUGIN_EXPOSE`. `MetamodPlugin` becomes `VoltMod::Plugin` with the same virtuals, so each plugin's `Plugin.cpp` changes by one base-class name.

Console commands: `volt list | status [name] | load <name> | unload <name> | reload <name>`.

### Phase 3. Do the repeated work once

Three small interfaces, each its own commit pair, each bumping `AbiVersion`. In every case the per-plugin code path is deleted, not kept beside the new one.

- **`IHostLog`: `Write(level, text, length)` and `MinLevel()`.** The SDK installs a `Log::SetHandler` handler that forwards to the host; the host prefixes the plugin's tag and prints. `MinLevel()` lets the SDK skip formatting below the level. The SDK keeps its own queue for worker-thread messages and forwards them on the game thread, so the host stays game-thread only. `volt log <name> <level>` sets one plugin's level. The host itself logs through the same sink.
- **`IHostGameData`: look up one resolved entry by name.** The host reads `gamedata.jsonc` and resolves it once, keeping the `ResolvedRecord`. `Lookup(kind, name)` returns a plain struct: found or not, an absolute address or an integer (slot index, offset), and a reason string owned by the host when unbound. The SDK's `Bindings` binds every member from this lookup and nothing else; the file reading and memory scanning (`GameDataDocument`, `GameDataResolver`) move into `src/Host/` and leave the SDK. `Bindings`' typed members and `Available()` reasons stay as they are; its SDK-free tests bind from a fake lookup. A broken signature after a game update is then logged once by the host, not once per plugin. `resolved.<platform>.json` is written by the host only.
- **`IHostSchema`: `LayoutStamp()` and `Verified()`.** The baked offsets live in each plugin's SDK copy, so the host can only vouch for a plugin built from the same generated layout. `voltmod schemagen` emits a stamp constant (a hash of the generated layout; add it if it does not exist yet). The host verifies its own copy once and writes the schema dump once. A plugin's `SchemaLayout` step compares its stamp with the host's and takes the host's result. A different stamp refuses the load with a message saying the plugin was built against another schema layout and must be rebuilt. `VerifySchemaLayout` and `WriteSchemaDump` move into `src/Host/` and leave the SDK.
- Verify: with three plugins the log shows one gamedata resolution and one schema verification; break one signature in `gamedata.jsonc` and confirm one error line and the same `Available()` reasons as before; `volt log anticheat warn` silences its info lines only; a plugin built against a changed schema manifest is refused with the rebuild message.

- **`Options<T>`.** First compare `plugins/admin-system/src/Config/ConfigManager.{hpp,cpp}`, `plugins/anticheat/src/Config.hpp` and `plugins/bhop/src/Config.hpp`, and build only what they share. Expected: load a glaze struct from `configs/settings.jsonc`, run an optional validate-and-derive step, publish the result in one move, keep the previous snapshot when a reload fails. Add a change event only if a plugin needs one. Switch bhop, anticheat and admin-system and delete `include/VoltMod/App/Config/JsonConfig.hpp` in the same commit pair; update `docs/config.md`.
- **Service container.** Two lifetimes. A singleton lives for the plugin load cycle: `AddSingleton<T>()`, `AddSingleton<TInterface, T>()`, `AddInstance<T>(T&)`. A transient is built fresh each time and owned by whoever asked: `AddTransient<T>()`, obtained only through `provider.Create<T>()` or an injected `Factory<T>`, both returning `std::unique_ptr<T>`. A transient may depend on singletons; naming a transient as `T&` in a `Deps` list is a compile error, because nothing would own it. There is no per-player scope (`PerSlot<T>` covers that) and no automatic construction of command handlers. A class names its constructor dependencies with `using Dependencies = VoltMod::Deps<ConfigManager&, DiscordReporter&>;`; no constructor deduction. The runtime's services are pre-registered as instances. `Build()` checks the graph once at load and returns `Status` naming a missing type or a cycle; construction follows dependency order, destruction is the reverse; the provider owns the objects, no `shared_ptr`. Tests are SDK-free. Write anticheat's `App` (`plugins/anticheat/src/App.hpp`) with the container on a scratch branch and show the user the two versions side by side. The user picks one shape. If the container wins, all three plugins, the scaffold and the docs switch to it and the hand-wired form is no longer taught; if it loses, the container is not merged. The two do not coexist.

## 5. Later, when third-party authors exist

- A compatibility policy. Until then there is none: `AbiVersion` must match exactly. Supporting a plugin built against an older SDK means append-only interfaces and versioned names, and is designed then, not now.
- A template repository that consumes only the published Conan package, built in CI on both platforms.
- With that policy, a lint that compares the boundary headers against a committed lock file.
- **Ask the user first:** moving the baked schema offsets into the host so a game update needs only a new host. Offsets stay generated at build time either way; this changes which binary carries them, at the cost of one indirection per field read.

## 6. Out of scope

- Third-party DI or loader libraries.
- A C function-table boundary. Pure-virtual interfaces are stable across MSVC versions and across GCC and Clang, and match what the engine and Metamod already do. A C table can be added later as a thin forwarding layer without touching existing plugins, as long as rule 2 holds.
- Moving `Database` or `Http` into the host. Logging moves only its output; formatting and the worker-thread queue stay in the SDK.
- Cached service handles and version ranges on dependencies. Point-of-use lookup and the exact `AbiVersion` match cover them.
- Managed-language plugins.

## 7. Risks and phase 0 answers

- Reload on Linux may not really unload; phase 0 item 2 decides. Do not document reload until it is settled.
- Fan-out order is new behaviour; today each plugin's hook runs independently in Metamod's order.
- A plugin crash still takes the server down. The host adds no isolation.

- **SourceHook is not used at all.** No `SH_DECL_HOOK`, `SH_ADD_HOOK`, `g_SHPtr` or
  `SourceHook::` anywhere. The eight engine hooks are `VoltMod::HookInterface` calls on KHook
  (`src/App/MetamodPlugin.cpp:114-165`), so the module-local `g_SHPtr` problem does not exist.
- **`g_PLID` is needed on exactly one line.** `PLUGIN_SAVEVARS()` expands to four assignments
  (`ISmmPlugin.h:514-518`); the only one taking the plugin's identity is
  `KHook::__exported__khook = ismm->GetDetourInterface(id)`. Everything else wants the shared
  `ISmmAPI*`. `g_PLAPI` is only ever `this`.
- **`g_SMAPI` has five uses, all replaceable.** `GetBaseDir`, `Format` (a `vsnprintf` wrapper),
  `GetEngineFactory`/`GetServerFactory` + `VInterfaceMatch` for the ten engine interfaces
  (`src/Runtime.cpp:59-98`), and `MetaFactory` in `ServiceExchange::Query`. The first four become
  the host's job once; the fifth becomes a direct lookup in the host registry, which leaves
  `Publish`/`Get<T>`/`Find` unchanged and makes `Get<T>()` unit-testable for the first time.
- **No `META_*` macro is used for convars or logging.** `Runtime` calls tier1's `ConVar_Register`
  directly (`src/Runtime.cpp:95-96`), so convars are already not attributed to a Metamod plugin.

**Item 1, KHook across the boundary.** `KHook::__exported__khook` is a plain non-exported global
defined once per module by `PLUGIN_EXPOSE` (`ISmmPlugin.h:490-495`), and every `KHOOK_API`
function in `khook.hpp` is a header-defined forwarder that dereferences its own module's copy.
Hidden visibility (`cmake/VoltModCommon.cmake:42-54`) makes that per-module split unavoidable.
So the host hands one `IKHook*` to each plugin at load and the plugin's own copy is seeded from
it, which is what `PLUGIN_SAVEVARS` already does. `IHost` therefore carries the KHook pointer as
planned. **Open, and the one thing to check before phase 2 lands:** whether
`ISmmAPI::GetDetourInterface(PluginId)` returns a process-wide singleton or a per-plugin adapter.
If it is per-plugin, the host owns one adapter for its own `PluginId` and every hosted plugin
shares it, and Metamod can no longer attribute or tear down hooks per plugin - the host's
per-plugin context becomes the only thing that can.

**Item 1, the sharpest constraint: allocators.** `memoverride.cpp` and `tier1/convar.cpp` are
compiled per plugin target (`recipes/hl2sdk-cs2/cmake/hl2sdk-sources.cmake:42-48`), and `/MT`
gives each module its own CRT heap. Ownership must not cross the host boundary in either
direction, which is what D2 already says; this confirms it is load-bearing, not stylistic.
`tier1/convar.cpp` stays per plugin so each plugin keeps its own pending-ConVar list, and the
host must not free a library that still has live registrations.

**Item 1, process-global statics to audit when the host becomes one module.** Each is written
today assuming one copy per plugin DLL: `src/Core/Files/Paths.cpp` `g_baseDir`,
`src/Engine/ConVars/ConVars.cpp:18` `g_changeCallback` (its comment says "Each plugin DLL owns one
ConVars instance and callback" - that assumption breaks), and the per-process schema field offset
cache (`include/VoltMod/Runtime.hpp:85`). The convar change callback is already on the phase 5
candidate list; this is why.

**Item 2. Not answered.** Load, hook, unhook, free, load again on Windows and Linux needs a real
host binary and a server. Verified in phase 2 and on the user's Linux test server, not before.

**Item 3. Not answered** for the same reason, but the ordering requirement is now precise:
`MetamodPlugin::Shutdown` (`src/App/MetamodPlugin.cpp:88-103`) runs custom hooks, commands,
`OnUnload()`, standard hooks, then the runtime. Every `Subscription` closure and every
`InstalledHook` thunk is plugin-module code that KHook holds a raw `this` and member address for
(`include/VoltMod/Unsafe/Hook.hpp:54-111`), so the host may not free a library until that whole
sequence has returned and no frame is in flight. Boundary rule 6's next-frame queue is what makes
that reachable.
